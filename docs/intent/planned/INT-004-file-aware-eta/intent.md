# Intent: 작은 파일이 많은 실행에서도 믿을 수 있는 남은 시간 표시

> 출처: 2026-11-03 Google Drive 대상 실제 실행(434MB·1,815개, 대부분 작은 파일)에서 "남은 시간 5시간 4분"이 표시된 건을 rclone 통계 1초 단위로 확인한 결과.

## 문제 (Problem)
- 실행 화면의 "남은 시간"은 rclone stats의 `eta`를 그대로 보여 준다(`log-parser.ts` `normalizeStats` → `etaSeconds`, `RunStatsGrid.tsx`). 앱의 계산 오류는 아니다.
- rclone `eta`는 "남은 바이트 ÷ 최근 전송 속도"로만 계산하고 파일 수를 반영하지 않는다.
- Google Drive처럼 파일 하나를 만들 때마다 처리 시간이 드는 대상에서는 작은 파일이 초당 0.3~0.5개만 올라가고, 그동안 바이트가 거의 늘지 않아 속도가 극단적으로 낮게 잡힌다.
- 그 결과 한 실행 안에서도 값이 크게 흔들린다. 같은 실행에서 관측한 값:

| 경과 | 처리 중인 것 | 속도 | rclone이 낸 남은 시간 |
| :--- | :--- | :--- | :--- |
| 19초 | 작은 파일들 | 22KB/s | 약 5시간 45분 |
| 67초 | 작은 파일들 | 1.2KB/s | 약 104시간 |
| 99초 | 114MB 파일 | 1.8MB/s | 약 3분 40초 |

- 실제 소요는 2시간 안팎(약 1.8시간)으로 추정된다. 바이트 기준(3~4분)도, 작은 파일 구간 값(5시간~104시간)도 아니다. 사용자는 실행을 중지할지, 기다릴지 판단할 근거를 잃는다.
  - 2026-11-03 로그 재확인: 이 실행은 2,302초에 1,815개 중 667개(초당 약 0.29개)에서 중단됐다. 같은 속도라면 전체 약 6,300초다(처음 기록한 "1시간 안팎"을 고침).

## 제안 결과 (Proposed outcome)
- 앱이 남은 시간을 직접 계산해 보여 준다.
  - 바이트 기준: 남은 바이트 ÷ 바이트 처리 속도
  - 파일 수 기준: 남은 파일 수(`totalTransfers - transfers`) ÷ 초당 처리 파일 수
  - 두 값 중 긴 쪽을 표시한다.
- 값이 안정되기 전(실행 직후, 표본이 부족할 때)에는 숫자 대신 "계산 중"을 표시한다.
- 작은 파일 구간과 큰 파일 구간이 번갈아 와도 표시값이 수십 배씩 튀지 않는다. 위 실행과 같은 조건에서 표시값이 실제 소요와 같은 자릿수(2시간 안팎)에 머문다.

## 영향 사용자 및 시스템 (Affected users and systems)
- 사용자: 수동 실행(미리보기·실제 실행) 진행 화면을 보는 사용자. 특히 Google Drive 등 파일당 처리 비용이 큰 remote 대상.
- main: `src/main/parsers/log-parser.ts`(`normalizeStats`, rclone `eta`·`speed`·`transfers`·`totalTransfers`·`elapsedTime`), 실행 통계 전달 경로(`src/main/services/run-service.ts`).
- shared: `src/shared/schemas/run.ts`(`typRunStats.etaSeconds`, 필요하면 "계산 중" 상태 표현 추가).
- renderer: `src/pages/RunStatsGrid.tsx`(남은 시간 칸), `src/shared/format.ts`(`formatDuration`).

## 제약 (Constraints)
- 안전 규칙 불변: 표시 전용 변경이며 실행·게이트·명령 인자(`command-builder.ts`)는 바꾸지 않는다.
- 계산은 순수 함수로 만들고 `tests/fixtures/rclone/`의 실제 stats 출력(작은 파일 다수 + 큰 파일 혼합)으로 단위 테스트한다. fixture에 실제 사용자 경로·remote 이름을 넣지 않는다.
- rclone stats 간격(현재 설정값)에 맞춰 이동 평균 등 평활화 창을 정한다. 새 의존성은 들이지 않는다.

## 결정 사항 (Decisions, 2026-11-03)
- **D-01 "계산 중" 해제 기준**: 아래를 모두 만족할 때 숫자를 표시한다.
  - 경과 10초 이상
  - 완료 파일 5개 이상 **또는** 바이트 진행률 5% 이상(큰 파일 하나뿐인 실행도 숫자가 나오도록)
  - 분모(전체 파일 수·전체 바이트)가 확정됨. rclone `totalTransfers`·`totalBytes`는 목록·비교 중에 계속 늘어나므로, 실행 전 비교 계획의 전송 개수·바이트를 분모로 쓸 수 있는지 spec 단계에서 확인한다. 쓸 수 없으면 `checks >= totalChecks`가 될 때까지 "계산 중"으로 둔다.
    - spec 보완(2026-11-03): 계획이 있으면 그것을 분모로 쓴다. 계획이 없으면 `totalTransfers`가 5초 동안 그대로일 때도 확정으로 본다. 대상에 같은 파일이 없는 copy는 `totalChecks`가 끝까지 0이기 때문이다(spec FR-2, §10 Q-2).
- **D-02 평활화**: 최근 N초 이동 평균은 쓰지 않는다. 작은 파일 구간과 큰 파일 구간이 번갈아 올 때 표의 흔들림을 그대로 재현하기 때문이다.
  - 계산은 실행 전체 누적 평균으로 한다.
    - 파일 기준: `경과 × 남은 파일 / 완료 파일`
    - 바이트 기준: `경과 × 남은 바이트 / 완료 바이트`
    - 두 값 중 긴 쪽을 쓴다.
  - 표시값에만 시간 상수 약 30초의 지수 평균을 걸어 초 단위 떨림을 줄인다. 계산값 자체는 누적값 그대로 둔다.
  - 한계: 큰 파일이 끝에 몰리는 등 파일 순서가 치우치면 누적 평균도 빗나간다. 목표는 "같은 자릿수"이므로 이 정도는 감수한다. 파일당 비용과 대역폭을 회귀로 추정하는 모델은 지금 범위 밖이다.
- **D-03 부분 전송분 반영**: 반영한다. 큰 파일을 받는 동안 완료 파일 수가 멈춰 파일 기준 ETA가 부풀고, "긴 쪽" 규칙 때문에 그 값이 표시되는 것을 막기 위해서다.
  - rclone stats의 `transferring[]`에서 파일마다 `bytes / size`(1 미만으로 제한)를 구해 `transfers`에 더한 소수값을 "완료 파일 수"로 쓴다.
  - `log-parser.ts`의 stats 스키마에 `transferring`을 선택 항목으로 추가한다. 파일 이름은 계산에 쓰지 않는다.
